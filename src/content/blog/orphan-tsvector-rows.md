有一次我發現搜尋索引的表裡，累積了一批指向已經不存在的資料的列。直覺的第一個念頭是：刪除的時候漏清了索引。我讓 AI 去修這個「刪除時沒有一併清理」的 bug，但它先回報的是：前提不對。

它做的事情是把整個程式碼庫搜過一輪。應用層只有一條刪除路徑，索引和主資料都在同一個 transaction 裡一起刪；用 `git log -L` 往回看，這幾行從刪除功能第一次上線就在，沒有歷史缺口。Schema 裡也沒有任何 `onDelete: Cascade` 指到這張表，沒有從父表連帶刪除的路徑；其他腳本和工具也都沒有刪過這張表的資料。刪除端沒有東西可以修。

真正的來源在寫入端。索引是用一段 raw SQL 的 `INSERT ... ON CONFLICT` 寫入的，而專案用的 ORM 把關聯放在應用層處理，資料庫層沒有外鍵擋著。更關鍵的是，建立和更新資料時呼叫這段寫入，都是 fire-and-forget，沒有 await。於是只要一筆資料在索引寫入落地之前就被刪掉，寫入照樣成功，孤兒列就這樣出現了。另一種向量索引的寫入形狀一模一樣，而且中間還夾著一次要好幾秒的外部呼叫，時間窗口更大。

修法很小。把 `INSERT ... VALUES` 改成 `INSERT ... SELECT ... FROM <主表> WHERE id = ...`：主資料還在就照寫，已經被刪就寫入 0 列，`ON CONFLICT` 的行為完全不變。所有呼叫端共用同一個函式，所以一處改動全部蓋住，另外補了兩個回歸測試。

有兩件事我決定不做。一是不把呼叫改成 await，因為那會把索引的延遲加進建立和更新的回應時間，而且現在正確性已經不依賴它了。二是不加資料庫外鍵，關聯放在應用層是整個專案的決定，不該為了一個 bug 改掉。

既有的孤兒列沒有放進這次修改，改成另外清理，這次只負責不再產生新的。

我覺得這件事最有意思的是驗證的方式：既然修法只擋新的孤兒，那過幾天再數一次，如果還是 0，就代表 guard 有效；如果又長出來，就表示還有我沒找到的寫入路徑。我全庫只找到兩處 raw INSERT，但這是唯一能證明我找漏了沒有的辦法。這個回頭數的動作我還沒做完，所以現在只能說「推論上擋住了」，不能說「已經證實」。
