前陣子把 AWS 的資源收進 Terraform，順手盤點了一遍監控，才發現有三個告警的狀態是 `INSUFFICIENT_DATA`，而且一直都是。這個狀態很容易被當成「沒事」，其實意思是它從頭到尾沒收到過資料。資料庫 CPU 點數用完、網站掛掉、後端大量報錯，這三種情況它們一封信都不會寄。

原因各不相同，但都是設定寫錯，不是真的平安無事。第一個是 metric 名稱多了個 `DB ` 前綴，真正的名字是 `CPUCreditBalance`。第二個是 Route53 健康檢查的 metric 只存在 us-east-1，告警卻建在別的 region，永遠讀不到。第三個有兩個問題：namespace 讀錯，而且 log metric filter 每次寫進去的值都是 0，就算讀對了也數不到任何錯誤。

當初收進 Terraform 時，刻意設定成「只匯入，不改行為」，所以這些錯誤也被原樣保留下來。這次是第一次有意識地去改。

改法本身不複雜。名稱改正；HTTPS 檢查的告警搬到 us-east-1，因為告警只能通知同 region 的 SNS topic，所以那邊也要新開一個 topic 和訂閱；filter 的值從 0 改成 1。

比較花功夫的是門檻。AI 一開始給的值是 CPU 點數低於 50 就告警、錯誤數大於等於 1 就告警，看起來都很合理，但沒有人拿真的資料驗證過。我把過去三天的數據拉出來，把各種門檻會觸發幾次算了一遍，結果兩個都不能用。

這台 RDS 每晚會停機省錢，所以點數每天早上都從 0 開始累積，大約要六小時才爬過 50。照原本的設定，每天早上都會固定收到一封假警報。我改成「每小時最低值低於 5，連續三小時」，只抓真正耗盡的情況。錯誤數也一樣：三天裡有 6% 的五分鐘區間出現過錯誤，門檻設 1 的話一天大概響十五次，吵到最後沒人會當一回事。最後設在五分鐘內 200 次，約每天兩次。這個數字是我看分布挑的，不是什麼標準答案，如果還是太吵，改成 400 就是約三天一次。

改完 apply 之後，我確認線上設定和程式碼一致，八個 stack 的 plan 都是 `No changes.`，六小時內沒有任何告警被觸發。

有一件事我還沒做，就是實際讓告警響一次。目前「出事時真的會寄信」只是從設定推論出來的，沒有實測。要測的話可以用 `aws cloudwatch set-alarm-state` 手動把 `HTTPS Check` 設成 ALARM，看信箱收不收得到。

另外有個意外的發現：這台 RDS 每天早上重啟時點數是 0，要等好幾個小時才會回到比較安全的水位。早上開工那段時間，資料庫可能一直處在點數不足的狀態。這是每晚停機省錢和早上效能之間的取捨，不在這次的範圍內，先記在這裡。

整件事讓我最有感的是：告警本身也要被驗證。建好告警不等於有在監控，至少該看一下它的狀態是不是 `INSUFFICIENT_DATA`，還有門檻在過去幾天的資料上會響幾次。
